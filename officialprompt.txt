You are the lead architect, kernel engineer, compatibility engineer, graphics engineer, and integration coordinator for SentinelOS.

4. PHASE A — FOUR PARALLEL AGENTS

AGENT 1 — Kernel Reliability and Scheduling

Mission

Audit and harden the kernel's reliability without unnecessarily replacing its architecture.

Inspect:

- Kernel initialization and shutdown paths.
- Interrupt and exception handling.
- Scheduler and thread lifecycle.
- SMP and per-CPU state.
- Synchronization primitives.
- Timer implementation.
- Kernel object lifetime and reference ownership.
- System call entry and return paths.
- Failure handling and diagnostics.

Required work

1. Find reproducible correctness defects.
2. Verify thread state transitions and cleanup.
3. Inspect scheduler races and incorrect per-CPU assignments.
4. Check interrupt safety and synchronization assumptions.
5. Audit kernel object lifetime and dangling references.
6. Check error handling for invalid system calls.
7. Prevent recoverable application failures from becoming unnecessary kernel crashes.
8. Add regression tests or targeted diagnostics for fixed defects.
9. Preserve existing behavior unless a demonstrated defect requires a change.

Acceptance criteria

- Existing scheduler tests pass.
- Fixed defects have reproducible tests where feasible.
- No new unexplained kernel faults are introduced.
- SMP claims are based on actual supported execution, not assumed hardware availability.

Do not rewrite the scheduler merely because a different architecture appears cleaner.

AGENT 2 — Memory Management and Process Isolation

Mission

Improve memory safety and application isolation.

Inspect:

- Physical memory allocation.
- Virtual address-space management.
- Page-table operations.
- Page permissions.
- User/kernel address separation.
- Process creation and destruction.
- PE32+ loading and mapping.
- Stack and heap setup.
- DLL loading and memory cleanup.
- Fault handling and process termination.

Required work

1. Audit allocation and deallocation paths.
2. Find memory leaks, double frees, use-after-free defects, and invalid mappings.
3. Verify that user-mode applications cannot obtain unintended access to protected kernel memory.
4. Check executable, writable, and read-only memory permissions.
5. Verify PE image bounds, section mapping and relocation handling.
6. Check cleanup after failed application startup.
7. Validate address-space lifetime during process termination.
8. Check page-fault reporting and process isolation.
9. Add regression tests for corrected failure cases.

Acceptance criteria

- Existing executable-loading tests continue to pass.
- Malformed executable inputs fail safely.
- Process cleanup does not leave invalid mappings or dangling references.
- Memory protections are verified against the actual architecture and implementation.

Do not claim complete process isolation unless the hardware and kernel enforce it.

It must be a real SentinelOS application using the existing executable format, application framework, GUI subsystem, system calls and configuration interfaces.

First inspect the current implementation and reuse the actual existing infrastructure. Implement missing foundational interfaces only where necessary.

Create the Settings application using the repository's established naming conventions.

Requirements:

- Build a real executable using the project's supported application format.
- Use the existing native window and control system.
- Give the application a proper Settings title and application identity.
- Integrate it with the existing desktop and Start menu where supported.
- Ensure the application can be launched through the actual shell/application-launch mechanism.
- Support normal window focus and closing behavior.
- Use the existing graphics pipeline.
- Preserve working mouse and cursor behavior.
- Handle unsupported system features gracefully.
- Provide meaningful failure messages.
- Ensure the app does not crash if a service or capability is unavailable.
- Integrate the app into the normal build and root-filesystem staging pipeline.
- Verify that it appears in the final generated OS image rather than merely existing in the source tree.

Do not invent a separate parallel GUI framework for Settings.

B. Required categories

Implement these categories with real functionality wherever the underlying OS exposes the necessary information and operations.

- OS name and version.
- Architecture.
- CPU information.
- Memory information.

3. Personalization

Provide:

- Available desktop appearance options.
- Supported theme or accent settings.
- Wallpaper controls only if the desktop implements wallpaper support.

Provide:

10. About SentinelOS

Display:

- Product name.
- Version and build.
- Architecture.
- Relevant kernel version.
- System capabilities.
- Diagnostic or version information.

C. Settings behavior

The Settings application must:

- Have working category navigation.
- Render controls through the existing GUI infrastructure.
- Show the actual current setting.
- Validate user input.
- Apply supported changes through real APIs.
- Report failures rather than silently ignoring them.
- Persist preferences when the system provides a reliable storage mechanism.
- Reload persisted values at startup.
- Handle unavailable APIs without crashing.
- Avoid blocking the entire GUI while retrieving information.
- Keep state consistent if an operation fails.
- Use clear labels and understandable errors.
- Avoid claiming unsupported functionality.

Implement search only if the existing input and UI framework can support it correctly.

D. Configuration architecture

Inspect whether SentinelOS already has a registry-like configuration facility, system configuration store, or suitable persistence mechanism.

Reuse it if it is appropriate.

If no suitable facility exists, design the smallest safe configuration layer necessary for Settings.

Requirements:

- Validate configuration files and values.
- Handle malformed or incomplete configuration.
- Preserve defaults when configuration is invalid.
- Avoid corrupting the previous configuration during writes.
- Use safe replacement or transactional semantics where the filesystem permits.
- Separate per-user preferences from machine-wide settings if the OS supports that distinction.
- Never store passwords, secrets or authentication tokens in plaintext as a shortcut.
- Document unsupported persistence guarantees.

Do not invent a registry merely to make Settings appear functional.

E. Settings tests

Add tests for:

- Application build and packaging.
- Application launch.
- Window creation and closing.
- Category navigation.
- Actual configuration retrieval.
- Supported setting changes.
- Invalid values.
- Failed system operations.
- Persistence and reload.
- Malformed configuration.
- Missing optional services.
- Regression of existing shell and GUI behavior.

Run the app inside the actual SentinelOS environment when possible.

If the available emulator cannot verify a capability, state that limitation explicitly.

F. Settings acceptance criteria

Settings is not complete merely because a window appears.

It must be:

1. Implemented in real source code.
2. Built as a real executable.
3. Packaged into the OS.
4. Discoverable and launchable from the shell.
5. Functional for the system operations actually supported.
